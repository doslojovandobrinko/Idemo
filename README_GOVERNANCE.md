# IDEMO GOVERNANCE INDEX

**The Primary Gateway and Master Directory of the IDEMO Governance Library**

---

## 1. Introduction & Purpose

IDEMO is not governed by isolated prompts, reactive hotfixes, or undocumented decisions. Instead, the IDEMO ecosystem is built upon a professional, structured, and permanent documentation framework.

This framework protects and guarantees:

- **Consistency:** Universal alignment of UI spacing, typography, data schemas, and API behaviors.
- **Quality:** Strict operational gates preventing functional, visual, or architectural regression.
- **Maintainability:** Modular software engineering practices designed to scale safely.
- **Scalability:** Standardized country expansion and curation onboarding protocols.
- **Architectural Integrity:** Local, offline-first client-side computation with zero remote data-leakage profiles.
- **Design Integrity:** Timeless, proprietary aesthetics that prioritize eye-safe readability under bright daylight conditions.
- **Long-Term Vision:** A high-end curation and concierge model designed for elite VIP events (such as Belgrade EXPO 2027).

Every development task, translation adjustment, database revision, and visual refinement must be fully traceable to one of the authoritative governing documents indexed in this directory.

### Hierarchy Rules

1. **The Creator — Sole Constitutional Authority:** The supreme, absolute constitutional authority. The Creator's latest instruction supersedes all existing rules, manifests, and documentation layers.
2. **The Principle of Non-Contradiction:** No subordinate document, local styling preference, or architectural implementation may contradict, weaken, or bypass a constraint established in a higher-level document.
3. **Delegated Limits:** All other roles (such as the Chief Design Guardian, QA Lead, or Operations Manager) operate under delegated permissions that may be amended or revoked by the Creator at any time.

## 3. Stable vs. Flexible Components

To ensure absolute security of IDEMO's identity while permitting fast, disciplined iteration, assets are categorized as either Stable or Flexible.

### Stable Components

These define the core foundations of IDEMO. They are highly protected and can be modified **only** through explicit Creator approval:

- **IDEMO Constitution** (Highest Governing Document)
- **Creator Authority Framework**
- **IDEMO Editorial Luxury Design Language**
- **Privacy-First Philosophy** (Zero tracking, local execution)
- **Offline-First Philosophy** & **Local State Management**
- **Mood Orbit Core Philosophy** (Continuous 2D spatial mapping)
- **Brand Identity** & **Core User Experience Principles**
- **Governance Framework** & **Documentation Hierarchy**
- **Architectural Principles** & **Type-Safety Standards**

### Flexible Components

These represent operational extensions of the product. They are designed to evolve continuously under delegated authority, provided they satisfy all Quality Gates and visual regression checks:

- **Country Datasets** & **Curation Assets**
- **Localizations** & **Translation Improvements**
- **QA Procedures**, **Operations Procedures**, and **Release Processes**
- **Content Updates** & **Image Asset Selections**
- **Knowledge Base Articles** & **Decision Register Logs**
- **Future Platform Integrations**

## 6. Single Source of Truth

To ensure clarity and eliminate maintenance overhead:

- **Duplicate Governance is Prohibited:** No rule, code checklist, color definition, or release protocol may be documented in more than one place.
- **Consolidation Rule:** If conflicting or duplicate policies are discovered, team members must immediately submit a consolidation proposal to merge the rules into the highest-ranking appropriate governing document.
- **No Inline Overrides:** Documentation should live in the files specified in this index. Inline markdown files within code folders must refer back to the centralized `/governance/` directory.

## 7. The Decision Framework

All changes to the IDEMO codebase, datasets, or visual structures must follow this six-step decision-making pipeline:

1. **Determine Scope:** Identify what needs to be changed.
2. **Identify Governing Document:** Find the authoritative folder and file.
3. **Verify Constraints:** Check higher-level documents for potential conflicts.
4. **Conduct Impact Assessment:** Document anticipated risks and benefits (Design Impact Review).
5. **Implement Minimum Change:** Implement the smallest compliant code patch.
6. **Verify and Log:** Run automated compile/lint tests, check for visual regressions, and record the entry inside `/governance/IDEMO_DECISION_REGISTER.md`.

---

## 8. Change Management & Revision Control

Governance documents are structural assets. Changes to Levels 1 through 6 must strictly adhere to the following:

- **Traceability:** Every modification must match an authorized entry in the decision log.
- **Historical Ledger:** Changes must be recorded chronologically, preserving previous versions of rules for auditing purposes.
- **Metadata Requirements:** Every amendment must document the affected document name, version tag, revision date, and approval authority.

## 9. AI Operating Principles

Every AI Coding Agent and Assistant operating inside the IDEMO workspace is bound to these principles:

- **Custodian Status:** You are a custodian of the IDEMO Design System and Architecture. Do not treat files as isolated tasks; protect the long-term maintainability of the entire product.
- **Read-Before-Write:** You must read the relevant files in `/governance/` before modifying code blocks or directories.
- **No Silent Redesigns:** If an instruction conflicts with the IDEMO Design Constitution, you must identify the conflict, explain which principles are affected, recommend the smallest compliant solution, and await explicit approval.
- **Strict Regression Auditing:** Every code edit must be verified using the Mandatory Regression Protection Checklist and validated by running syntax compilation and linting tests.
